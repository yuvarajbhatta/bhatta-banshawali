# 07 — Migration Plan

## Findings from running `scripts/migration-rehearsal.sh` (2026-07-30)

- **`app_users.id` had no `AUTO_INCREMENT` in the live production schema — fixed (2026-07-30).** `V1__baseline_schema.sql` always declared `id BIGINT NOT NULL AUTO_INCREMENT`, but the live table and the migration file had drifted apart (confirmed via a schema-only `mysqldump --no-data` against prod, no PII involved). It was dormant: the only code path that inserts a *new* `app_users` row is `AdminUserInitializer` → `AppUserService.registerAdminIfMissing`/`registerUserIfMissing` at startup, and it no-ops whenever the configured username already exists — which it always had, in every real deploy so far. It surfaced during a migration rehearsal because that run's `app.admin.username` didn't match an existing row, forcing a real insert, which then failed on the missing default. Fixed via `V13__fix_app_users_id_auto_increment.sql` (`ALTER TABLE app_users MODIFY id BIGINT NOT NULL AUTO_INCREMENT`) — verified against a copy of production data first (via `scripts/migration-rehearsal.sh` and an isolated manual check confirming the AUTO_INCREMENT counter correctly picked up `MAX(id)+1`), then deployed. Confirmed live: `SHOW CREATE TABLE app_users` on prod now shows `AUTO_INCREMENT`, and `flyway_schema_history` records `V13` as successful.

## Guiding Constraint

**Never delete the existing database.** All steps below are additive/reversible until an explicit, confirmed cutover step, which itself is preceded by an immutable backup.

## Step-by-Step Plan

1. **Inventory existing tables and records.** Direct, read-only query pass against the live MySQL instance (row counts for `persons`, `relationships`, `app_users`; distribution of `relationship_type`; NULL rates on `generation_number`, name fields). This has not been done as part of this repository inspection — it requires direct database access and must happen before schema work begins.
2. **Detect data quality problems.** Duplicate `(person_id, related_person_id, relationship_type)` rows (no DB constraint currently prevents this — see `01-current-system-assessment.md`), orphaned relationships (referencing deleted persons, if any FK constraints are absent), cycle detection (a person who is their own ancestor via `PARENT_OF`/`CHILD` chains), and multiple candidates for `getRootPersonForLineage()`'s "person with no incoming CHILD edge" heuristic (today the code silently picks `.findFirst()` — the real data may contain more than one, which must be surfaced, not hidden).
3. **Map old entities to the new model** per the table in `04-data-model.md` (`AppUser`→`UserAccount`+`Role`, `Person` flat name fields→`PersonName` rows, `FATHER`/`MOTHER`/`CHILD`/`SPOUSE`→`PARENT_OF`/`SPOUSE_OF`).
4. **Normalize English and Nepali names** into the new `PersonName` structure, re-running (not discarding) the existing `NameTransliterationService` logic as a *suggestion* pass only, never overwriting explicit values — exactly the guarantee `PersonService.backfillMissingNepaliNames`/`clearAutogeneratedNepaliNames` already implement today, which must be preserved.
5. **Preserve existing primary key IDs** for `Person` and `Relationship` rows where at all possible (deep-linkable URLs, any external references) — introduce a durable ID-mapping table only where a genuine collision or restructuring (e.g., `CHILD` edges collapsing into derived-not-stored) makes preserving the literal ID impossible.
6. **Migrate people** into the new `Person` + `PersonName` tables via a versioned migration script (Flyway), rehearsed first against a disposable copy of production data (see step 13).
7. **Migrate relationships** into the new `Relationship` table with updated `RelationshipType` values, applying the DB-level uniqueness constraint only after step 2's duplicate-detection pass confirms (or cleans) the source data.
8. **Detect cycles and orphan links** as an explicit, scripted validation step post-migration (not assumed clean because step 2 ran once against the old schema — re-verify against the migrated data).
9. **Migrate users.** Existing `AppUser` rows (username, bcrypt-family password hash, role string) migrate into `UserAccount` (username becomes a placeholder unless a real email is separately collected — see Open Question below) + a proper `Role` FK.
10. **Securely handle existing password hashes.** `DelegatingPasswordEncoder` output (already bcrypt by default) is compatible and can be carried over directly into the new `UserAccount.passwordHash` field without forcing a reset, *provided* the encoding prefix is preserved as-is (Spring Security's delegating encoder format, e.g. `{bcrypt}...`) — verify this explicitly against a sample of real hashes during the dry run rather than assuming compatibility.
11. **Link users to person records only after verification** — this is the single largest manual/semi-manual step, since no existing signal links today's `AppUser` rows to `Person` rows. Plan for an admin-driven reconciliation UI (or a one-time spreadsheet-assisted pass, if the user count is small — confirm actual count in step 1) rather than assuming automation is possible.
12. **Validate row counts and relationship counts** — migrated row counts must reconcile exactly against the step-1 inventory (accounting for any deliberate `CHILD`-edge collapsing into derived relationships, which should reduce `Relationship` row counts in a predictable, documented way, not an unexplained one).
13. **Run dry-run migrations** against a full copy of production data. **Decided (2026-07-30)**: no persistent staging environment (see `03-target-architecture.md`) — instead `scripts/migration-rehearsal.sh` dumps prod read-only, loads it into a disposable Docker MySQL container, and starts the app against that container so Flyway runs for real. Run this before any migration-bearing deploy, not just at cutover.
14. **Test rollback** — confirm the pre-migration backup can be restored and the old application version can run against it, before attempting any production cutover.
15. **Create reconciliation reports** — a written diff (counts, sample spot-checks, any records requiring manual admin follow-up) reviewed by the maintainer before cutover.
16. **Keep an immutable backup before cutover** — a `mysqldump` (or equivalent) taken immediately before the schema migration runs, stored outside the production host.

## Sequencing Relative to the Architecture Rewrite

The schema migration (this document) should land **before** the Next.js frontend replaces Thymeleaf, so that the new Spring Boot REST API and the new schema can be validated together first against the existing Thymeleaf UI (temporarily adapted to the new controllers) before the frontend rewrite begins. This avoids debugging two large simultaneous changes (schema + entire frontend) at once.

## Open Questions Requiring User Input

1. **Do existing `AppUser.username` values correspond to real email addresses, or are they arbitrary handles?** This determines whether email collection for existing users can be automated or requires manual outreach.
2. **How many existing `AppUser` rows actually exist?** (Not visible from the repository — direct DB access needed.) This determines whether user-to-person linking can be a guided one-by-one admin flow or needs bulk tooling.
3. **Are `FATHER` and `MOTHER` relationship types used interchangeably with generic parent semantics anywhere in current data**, or is the sex-of-parent distinction load-bearing for existing UI logic? This determines whether they collapse into a single `PARENT_OF` type (with a `parentRole` attribute) or remain distinct types in the target model.
